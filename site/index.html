src/domain/workflow.ts

Um fluxo explícito, com um portão no meio

A sessão é uma máquina de estados com tabela de transições. A única aresta para executing sai de awaiting_approval e só é percorrida por approvePlan(), que é uma ação humana. Transição inválida lança erro, e isso está coberto por teste.

01 · draft

Solicitação

Você descreve a tarefa. O Orchestra abre a sessão no projeto ativo.

02 · planning

Plano

O Planner devolve tarefas em JSON, validadas antes de aparecer na tela.

03 · awaiting_approval

Aprovação

Aprovar, rejeitar com motivo ou pedir ajuste. Sem clique, nada anda.

04 · executing

Execução

O Builder propõe diffs. Nada é gravado no disco nesta versão.

05 · reviewing

Revisão

O Reviewer aponta riscos e testes faltando. A sessão fecha como concluída.

Saída de modelo é dado não confiável. Plano, diffs e revisão passam por src/providers/parse.ts: tipos, limites de tamanho e caminhos. Diff com ../, caminho absoluto, letra de drive, ~ ou UNC é recusado e a sessão vai para failed.
PROGRESS.md · ROADMAP.md

O que já funciona e o que ainda não existe

Sem promessa: o que está na esquerda roda hoje e tem teste; o resto está no roadmap.

Funciona hoje

  • Fluxo completo solicitação → plano → aprovação → execução → revisão, com cancelamento por AbortSignal.
  • Provedor OpenAI-compatível (OpenAI, OpenRouter, Groq, Ollama, LM Studio) com 401, 429, timeout e rede tratados.
  • Modo demonstração offline, sem chave e sem rede, para ver o fluxo inteiro.
  • Chave no Gerenciador de Credenciais do Windows no app desktop, via comando Rust.
  • Chat direto com cada agente, projetos, sessões e conversas salvos localmente.
  • CI em Windows e Ubuntu: lint, typecheck, Vitest, build, clippy, gitleaks.

Ainda não existe

  • Ler arquivos do projeto como contexto (allowlist de diretório, negação de .env e chaves).
  • Aplicar diffs aprovados no disco, com aprovação por arquivo.
  • Chamadas HTTP pelo lado Rust, para a chave não passar pelo JavaScript.
  • Persistência em SQLite, exportação de sessão e instalador publicado.
  • Execução de comandos: só com isolamento demonstrado. Não há sandbox hoje.
  • Mascotes dos agentes (os espaços já estão reservados na UI).
README.md

Rodar na sua máquina

Node.js 22 ou mais recente. O app desktop precisa também de Rust (MSVC) e das C++ Build Tools no Windows.

navegador 
git clone https://github.com/Efer-Eder/agent-orchestra.git
cd agent-orchestra
npm install
npm run dev   # http://localhost:5173
desktop (Windows) 
winget install --id Rustlang.Rustup
rustup default stable-msvc
npm run tauri dev
npm test      # Vitest
Sobre a demo hospedada aqui: ela é o mesmo build do frontend, em modo demonstração (respostas fixas, sem rede). Se você configurar um provedor nela, a chave fica só na memória da aba e a chamada vai direto do seu navegador para o provedor; nada passa pelo efer.online. Alguns provedores bloqueiam chamadas de navegador (CORS); no app desktop isso não muda, então teste com um servidor local como Ollama ou LM Studio.

Arquitetura em uma tela

O domínio é TypeScript puro, sem I/O, com dependências injetáveis (ids e relógio) para testes determinísticos. O shell Rust é mínimo de propósito.

Provedores

Contrato AgentProvider com plan, build, review e chat, todos com AbortSignal. Mock e OpenAI-compatível implementam o mesmo contrato.

Shell Tauri

Sem plugins de fs, shell ou http. Três comandos de chave, cada um liberado por permissão explícita. CSP restritiva. Nenhuma telemetria.

Segredos

keyring-core + store nativo do Windows. A chave nunca vai para localStorage, logs ou mensagens de erro; há teste garantindo isso.
